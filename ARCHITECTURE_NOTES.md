# Xavier LIMS — Architecture Notes

Reference document capturing key design decisions, long-term risks, and open
questions discussed during development. Intended as a thinking aid, not a
formal spec. Update as decisions are made.

---

## Natural Key Design

### Decision
Users never interact with internal IDs (XP00001, XS00042, etc.). Every ingest
endpoint accepts human-readable names and resolves them to foreign keys
internally. Internal IDs are generated by the database and only surfaced in
query results for reference.

### Rationale
Lab members fill in spreadsheets with sample names, project names, and assay
types — not database IDs. Requiring IDs would demand a lookup step before every
ingest, which breaks the CSV workflow entirely.

### Where it strains
Natural key resolution in a hierarchical schema produces chains. Creating a
file currently requires four natural keys (sample_name, assay_type,
library_prep_date, flowcell_id) to resolve a single flowcell_library_id. As
the hierarchy deepens, these chains grow.

### The CSV vs UI split
The two ingest paths do not need the same resolution strategy:
- **CSV upload** — must use natural keys; users write names in spreadsheets.
- **Manual entry (UI)** — can use dropdowns that fetch existing records by name
  but submit IDs directly. The form does the resolution, not the backend.

This means the `project_name` propagation (below) only lives in the CSV path.
The manual entry form can evolve to use dropdowns and skip the chain.

## Sample Name Scoping

### Problem
The original implementation resolved `sample_name` globally:
```sql
SELECT id FROM samples WHERE sample_name = %s
```
Two projects with a "SAMPLE-001" would silently collide — the wrong sample
would be resolved with no error.

### Decision
`sample_name` is unique **within a project**, not globally. Enforced by a
composite database constraint:
```sql
UNIQUE (project_id, sample_name)
```
Every endpoint that resolves via `sample_name` now also requires `project_name`
to scope the lookup.

### Propagation
The following models and endpoints were updated to require `project_name`:
- `sample_sources` — scopes the sample lookup
- `experiments` — scopes the sample lookup
- `cohort_members` — scopes the sample lookup
- `pool_members` — scopes through experiment → sample
- `flowcell_libraries` — scopes through experiment → sample
- `files` — scopes through the full chain

### Templates impact
All templates for the above entities now include a `project_name` column.
This is correct: a user creating an experiment should always specify which
project's sample they mean.

## Schema Hierarchy

### Current depth
```
Projects → Samples → Experiments → Flowcell Libraries → Files
```
Five levels of lineage. Junction tables (sample_sources, cohort_members,
pool_members) branch off but do not add depth.

### Why the depth is real
This structure mirrors the ENA (European Nucleotide Archive) model:
Study → Sample → Experiment → Run → Files — the global standard for sequencing
data submission. The hierarchy reflects genuine biological and technical
distinctions, not over-engineering.

### Sample vs Experiment — keep separate
A single biological sample regularly produces multiple independent library
preparations (different assay types, different dates, multiome data). The
Sample / Experiment separation is necessary. Merging them into a single
"Library" table would lose the ability to track multiple assays per sample.

**Decision: keep separate.**

### Flowcell Libraries — worth monitoring
A flowcell library is the join between an experiment and a sequencing run,
plus lane and index metadata. It exists to pre-register samplesheet assignments
before sequencing data arrives.

If in practice flowcell libraries are always registered at the same time as
files (post-sequencing, never in advance), this table's purpose weakens and its
fields could migrate to the files table, removing one level from the chain.

**Decision: keep for now. Revisit if the pre-registration use case never
materialises in practice.**

## Long-Term Risks

### Critical

**1. No connection pooling**
Each Cloud Run instance opens its own psycopg2 connection to Cloud SQL.
Cloud SQL's default connection limit (~100) is exhausted quickly under
concurrent use. Under autoscaling, Cloud Run makes this worse — more instances
means more connections, faster exhaustion.
*Fix: PgBouncer sidecar, or Cloud SQL's built-in connection pooling proxy,
before real load hits.*

**2. No audit trail**
There is no record of who submitted what, when, or with what payload. In a lab
setting, data provenance is important. A bad batch ingest corrupting 500 sample
records leaves no trace for recovery.
*Fix: `submission_log` table — user, entity, action, payload JSONB, timestamp.*

**3. Hard deletes only**
Deletions are permanent with no recovery path. One accidental delete wipes
lineage permanently (cascade ON DELETE removes all downstream records).
*Fix: `deleted_at TIMESTAMPTZ` soft-delete column, filtered from all normal
queries. Planned once auth is in place.*

**4. No authentication**
Any user with the URL can read or write. As usage grows, "who changed what"
becomes a question with no answer. Auth also enables per-user logging and
write-permission scoping.
*Status: deferred until power users are comfortable with data entry workflows.*

### Important

**5. No controlled vocabularies**
Free-text fields (`assay_type`, `organism`, `tissue`, `cohort_type`) will
diverge over time. "scRNA-seq", "scrna-seq", "10x RNA" will coexist for the
same assay. Querying and dashboarding become unreliable.
*Fix: Enum validation at ingest time + XLSX templates with embedded dropdowns.
Vocabularies defined in `schema.py`.*

**6. Manual schema migrations**
Schema changes are applied as ad-hoc SQL. Dev and prod have already diverged
(sample_type column, subjects table). Without a migration runner, every schema
change is a manual coordination step that compounds as the team grows.
*Fix: Alembic, or at minimum a disciplined numbered migration file convention
(already started in migrations/).*

**7. JSONB extra_metadata as a data gravity well**
Because extra_metadata accepts anything, important structured fields tend to
accumulate there instead of becoming proper columns. JSONB is harder to query
and index at scale. GIN indexes are not yet present.
*Rule of thumb: if a field appears in >20% of records, promote it to a real
column. Add GIN index if JSONB queries become slow.*

**8. No read replica / analytics separation**
Heavy dashboard queries (multi-table JOINs across projects/samples/experiments)
run on the same Cloud SQL instance as writes. Under real load these contend.
*Fix: Cloud SQL read replica for dashboard and custom SQL queries.*

### Architectural (slower burn)

**9. Streamlit scalability limits**
Streamlit reruns the full script on every interaction. With large datasets,
`st.data_editor` loading full tables becomes slow. Pagination and server-side
filtering will be needed before the Browse tab degrades.

**10. File existence validation**
The files table stores GCS URIs but does not verify the file exists, monitor
for moves, or catch lifecycle-policy deletions. The files table can become
stale silently.

## Decisions Made

| Topic | Decision |
|---|---|
| Natural key resolution | Keep — correct for CSV ingest path |
| sample_name uniqueness | Project-scoped UNIQUE(project_id, sample_name) |
| Sample vs Experiment | Keep separate — multiple assays per sample are real |
| Flowcell Libraries table | Keep — revisit if pre-registration never used |
| XLSX templates | Implement with embedded dropdown validation per vocabulary |
| Auth / submission log | Deferred — after power users are onboarded |
| Alembic | Deferred — using numbered SQL migration files for now |

---

## Open Questions

- Should `sample_name` be enforced as globally unique in practice as a lab
  convention, or truly allow collisions across projects?
- When does `flowcell_libraries` earn its keep vs getting absorbed into `files`?
- Which fields in `extra_metadata` have appeared consistently enough to be
  promoted to real columns?
- Connection pooling: PgBouncer sidecar vs Cloud SQL Proxy built-in pooling?
- Soft delete: at which tables does it matter most? (samples and files are
  the obvious candidates — losing those cascades everything downstream)
